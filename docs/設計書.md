# 文書管理システム 設計書(案)Rev.0.1

## 1. 目的と方針
- 作業手順書などの文書について、**版管理・承認・周知・改訂履歴・操作ログ**を一元管理し、内部/外部監査で「いつから・誰が・なぜ」を即答できるようにする。
- **GitHubはソースコード・設計書・テスト(ダミーデータ)のみ**を保存する。社外秘の文書・DB・ログは**社内サーバー/PCのみ**に置く。
- Microsoft Graph、Power Automate等のクラウド連携には依存しない(単体で完結)。
- 小さく始め、監査で必須の機能から実装する。

## 2. 機能要件
### 2.1 必須(フェーズ1)
| ID | 機能 | 内容 |
|---|---|---|
| F01 | ユーザー・権限 | 個人ID+パスワード(ハッシュ化)。役割:管理者/作成者/確認者/承認者/閲覧者。共有アカウント禁止 |
| F02 | 文書台帳 | 文書番号、名称、分類、所管部署、状態、現行版、見直し期限 |
| F03 | 版管理 | 文書ごとに版(Rev.)を保持。上書き禁止、改訂は新版として登録 |
| F04 | ファイル保管 | PDFを正本として保存。SHA-256ハッシュを記録し、改ざん検知 |
| F05 | 承認ワークフロー | 作成中→確認中→承認済→適用中→廃版。確認者・承認者の日時を自動記録。差戻し可 |
| F06 | 改訂履歴 | 版ごとに改訂内容・改訂理由(必須入力)、制定日、改訂日、**適用開始日**を保持。履歴表を自動生成 |
| F07 | 閲覧 | 現場は「適用中」の最新版のみ閲覧。旧版は管理者・監査用画面のみ |
| F08 | 操作ログ | ログイン、閲覧、登録、承認、廃版を記録。**更新・削除不可**(ハッシュチェーン) |
| F09 | 監査出力 | 文書台帳、改訂履歴、承認記録をExcel/CSV/PDFで出力 |

### 2.2 重要(フェーズ2)
| ID | 機能 | 内容 |
|---|---|---|
| F10 | 周知・教育記録 | 版ごとの閲覧確認(既読)・教育実施日・受講者署名。適用開始日より前に教育があるかチェック |
| F11 | 見直し期限管理 | 期限の近い文書を一覧表示。メール通知(社内SMTP)任意 |
| F12 | 関連文書リンク | 手順書↔様式↔設備(酸欠計等)の紐付け |
| F13 | 整合性チェック | 必須項目欠落、承認済なのに適用開始日なし、教育未実施での適用、等を一覧化 |
| F14 | 設備・保護具台帳 | 酸欠計・墜落制止用器具の校正期限、使用開始日 |

### 2.3 後回し
全文検索、モバイル最適化、QRコード、多言語、電子署名。

## 3. 非機能要件
- **機密性**:社内LAN内のみ公開。HTTPS(社内証明書)。ファイル・DBへのOS権限を最小化。
- **完全性**:版の上書き禁止、ファイルハッシュ、ログのハッシュチェーン。
- **可用性**:日次バックアップ(別機器+別拠点/オフライン媒体)。年1回の復元テストを記録。
- **保守性**:設計書・運用手順書・引継ぎ者の明記。自動テストを備える。
- **保存期間**:文書・ログとも規程で定める期間(例:5年以上)削除しない。

## 4. 技術選定
| 項目 | 採用 | 理由 |
|---|---|---|
| 言語 | **Python 3.12** | AIとの相性が良く、情報が豊富 |
| Webフレームワーク | **FastAPI** + Jinja2テンプレート | 軽量。画面もサーバー側で描画しJS最小 |
| DB | **SQLite**(同時利用が増えたらPostgreSQLへ) | 導入不要、ファイル1つでバックアップが容易 |
| ORM/移行 | SQLAlchemy + Alembic | スキーマ変更の履歴管理 |
| 認証 | セッション+パスワードハッシュ(argon2) | 外部サービス不要 |
| 帳票出力 | openpyxl(Excel)、WeasyPrint等(PDF) | 監査提出用 |
| テスト | pytest | 版管理・ログ改ざん検知の回帰防止 |
| 品質 | ruff(静的解析)、pre-commit、GitHub Actions(ダミーデータでテストのみ) | 機密を渡さずCI |
| 配布 | 仮想環境(venv)+requirements.txt固定。Windowsならサービス化(NSSM)またはDocker | 再現性のある導入 |

## 5. 構成
```
[ブラウザ(社内LAN)] → HTTPS → [FastAPIアプリ(社内サーバー)]
                                   ├─ SQLite (data/app.db)
                                   ├─ 文書ファイル (data/files/)
                                   └─ 日次バックアップ → 別機器/別拠点
[GitHub(プライベート)] ← コード・設計書・ダミーデータのみ
```
本番へはGitHubのリリース(タグ)を手動で取り込み、更新手順と実施記録を残す(システムの変更管理)。

## 6. データモデル(主要テーブル)
- **users**(id, login_id, name, role, password_hash, active)
- **documents**(id, doc_no, title, category, department, status, review_cycle_months, next_review_date)
- **revisions**(id, document_id, rev_no, file_path, sha256, enacted_date, revised_date, **effective_date**, change_summary, change_reason, status, created_by, created_at)
- **approvals**(id, revision_id, step[作成/確認/承認], user_id, decision, comment, decided_at)
- **acknowledgements**(id, revision_id, user_id, acknowledged_at, training_date)
- **equipment**(id, name, model, calibration_due, in_use_since, note)
- **doc_links**(id, from_document_id, to_document_id / to_equipment_id, type)
- **audit_log**(id, timestamp, user_id, action, target, detail, prev_hash, hash) ← 追記のみ

## 7. 主要ルール
1. 承認済み版は編集不可。変更は必ず新版(Rev+1)として作成。
2. 改訂理由が空の版は確認へ進めない。
3. 作成者本人は自分の文書を承認できない。
4. 適用中にできるのは承認済み版のみ。新版を適用中にすると、旧版は自動で廃版(削除はしない)。
5. 適用開始日は承認日とは別に入力。教育日が適用開始日より後なら警告。
6. audit_logは各行に前行のハッシュを含め、検証コマンドで改ざんを検知する。
7. DBユーザーにもUPDATE/DELETEを許さない(audit_log・approvals)。

## 9. リポジトリ構成案
```
docmgmt/
├─ app/ (main.py, models.py, routes/, services/, templates/)
├─ tests/ (ダミーデータのみ)
├─ migrations/
├─ docs/ (設計書、運用手順書、バックアップ手順)
├─ scripts/ (バックアップ、ログ検証)
├─ .gitignore (data/, *.db, .env を除外)
└─ requirements.txt
```

## 11. 運用・リスク
| リスク | 対策 |
|---|---|
| 作成者の異動で保守不能 | 設計書・運用手順書、副担当者の指名 |
| 単一PCの故障でデータ消失 | サーバー機で稼働、日次バックアップ、復元テスト記録 |
| 規程とシステムの不一致 | 規程にシステム運用を明記し、変更時は同時改訂 |
| 過去の版の復元が困難 | 移行時、現行版と判明分の旧版を登録し、不明な適用日は推測せず根拠を記録 |
| 機密のGitHub混入 | `.gitignore`、pre-commit、レビュー |
| 脆弱性 | 依存ライブラリの定期更新、アクセスはLAN内のみ |

## 12. 未決事項(要確認)

- 認証方式(個別ID/社内AD連携の要否)
- ISO認証の有無、監査側の要求事項
